        How Mini DFS works

        A small file storage system modelled on HDFS. It splits files into 1 MB chunks, keeps two copies of every chunk on different storage nodes, and still returns the complete, unchanged file when a node fails. When a node stays down, the master copies its chunks to a healthy node so every chunk has two copies again.

        Client client.py

        • Splits a file into 1 MB chunks and computes a SHA-256 per chunk and for the whole file.
        • Asks the master where chunks go, then sends the bytes directly to the storage nodes.
        • On download, tries the next copy when a node is down or a chunk is damaged.

        Master master.py · :5000

        • Never stores file data, only metadata: files, chunks, and which nodes hold each chunk (metadata.json).
        • Places chunks on the least-loaded live nodes.
        • Watches heartbeats, marks silent nodes dead and repairs lost copies.

        Storage nodes storage_node.py · :5001–5003

        • Save, return, list and delete chunks in their own folder, storage/node_<port>/.
        • Send a heartbeat to the master every 3 s.
        • Copy a chunk straight to another node when the master asks (re-replication).

        The five flows

        1

        Upload

        1. Client → master POST /allocate: “I have 3 chunks, where do they go?”
        2. Master picks the 2 least-loaded live nodes per chunk.
        3. Client → nodes PUT /chunks/<id> with the chunk’s SHA-256; a node rejects a chunk whose checksum does not match.
        4. Client → master POST /commit with where each chunk landed.
        2

        Download

        1. Client → master GET /files/<name> for the chunk map and live copies.
        2. For each chunk: read from the first live copy GET /chunks/<id>, verify its SHA-256.
        3. Node down or bad checksum → try the other copy.
        4. Verify the whole file’s SHA-256 before saving it.
        3

        Failure detection

        1. Every node sends POST /heartbeat every 3 s.
        2. The master’s monitor runs every second.
        3. A node silent for more than 10 s is marked dead.
        4. Reads keep working during those 10 s because the client falls back to the second copy.
        4

        Self-healing

        1. The master finds every chunk with fewer than 2 live copies.
        2. It picks a healthy, least-loaded node that does not hold the chunk yet.
        3. It tells a surviving holder POST /replicate: the chunk goes node → node, never through the master.
        4. The chunk map is updated and saved.
        5

        Rejoin

        1. A restarted node sends its first heartbeat; the master marks it alive again.
        2. The master asks it for its chunk list GET /chunks.
        3. Copies that were re-created elsewhere while it was away are stale and get deleted.

        Why no data is lost

        Every chunk lives on 2 different nodes, so any single node can fail at any moment. Checksums catch damaged chunks on both upload and download, and writes go to a temporary file first, so a half-written chunk is never visible.

        Known limitations

        • Single master. The master is a single point of failure; real HDFS adds a standby master.
        • One machine. All nodes run on one laptop, so real network delays are not tested.
        • Write once. Files cannot be edited after upload, only replaced (as in HDFS).
        • Fixed cluster. Three storage nodes on fixed ports; adding nodes means editing config.py.
        • Dashboard-only admin. The admin sign-in guards this dashboard. The master and node APIs stay open, so client.py needs no password and anyone on this laptop can still call them.
